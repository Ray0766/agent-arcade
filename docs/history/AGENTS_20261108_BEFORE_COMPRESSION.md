## 有作者判断的 UI 与内容

- 用本项目真实对象和核心任务组织界面。设计较大变化前，简短比较两个可行方向，选择一个并说明理由；定义必要的字号层级、字体及中文回退、间距、色彩语义、密度和动效用途。
- 避免无理由套用通用 SaaS 外观：大渐变标题、等宽卡片墙、装饰性统计、泛用仪表盘、每段都编号、全页面入场动画。它们不是绝对禁用；使用时必须服务信息层级和任务。
- 一个页面优先突出一个核心行为。动效解释状态或操作结果；空间、字体、内容密度和交互细节共同形成特色，不能只换配色。
- 用具体名词、真实例子和明确动作写文案。按钮说明将发生什么，空状态给起步方法，错误说明原因与可执行下一步。删掉“赋能、革命性、无缝、极致”等无依据宣传。
- UI、README、样例、报告与演示使用一致术语。禁止虚构数据、用户评价、客户标志、奖项、性能结果与完成度；合成样例须标明。
- 按产品支持范围检查窄窗口/缩放、键盘、焦点、对比度、长文本、中文、减少动态效果。网页以 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 的相关条款为基准，原生应用补充平台规范；未全面审计不能宣称全面合规。

## 实现、验证与交付

- 先交付端到端最小闭环，使用已有成熟组件解决通用问题。技术栈依据约束选定，不预设必须上云、多 Agent、向量数据库或完整后台。
- 核心功能必须有真实输入、处理、输出与恢复路径；加载、空数据、损坏输入、失败、取消及必要的撤销/重试要按风险覆盖。对输入格式、工作量、内存与并发设置合理边界。
- 默认保护本地素材和日志；联网、模型调用、遥测及费用要明确。密钥不写入仓库、截图或导出文件；外部内容不能成为执行指令，样例不得产生未经授权的外部副作用。
- 用可复现样例验证主要风险和本项目亮点，覆盖有效输入与必要的反例。指标先定义口径、目标机器、数据规模和对照方法，再报告结果；不能用编造的“提升百分比”。
- UI 变更必须实际运行并检查关键状态截图；视频、PDF、导出报告要打开最终文件审查。编译成功、测试通过或浏览器没有报错，都不能替代用户流程验证。
- 发布里程碑应能从干净环境按 README 完成首次成功；尽量提供无需账号或付费密钥的样例体验。演示展示真实功能，说明输入、结果与限制，不用假按钮或模拟成功冒充成品。
- 保持模块边界清楚、命名贴合领域，复用现有约定；避免未经需要的抽象和大依赖。公开发布前检查源码及样例许可、首次运行说明、真实截图/演示与贡献入口，让外部开发者能理解、运行并修复一个小问题。
- 测试应对应实际风险；不为凑覆盖率写实现镜像测试，纯文档改动只需内容、链接和一致性检查。检查通过后，除新改动、失败或实质疑点外不反复追加验证。
- 收尾提供变更路径、关键验证结果和未解决限制；只有核验后才能宣称已提交、推送或上线。长任务在仓库内维护简洁进度，保留决定、证据路径与下一步。
