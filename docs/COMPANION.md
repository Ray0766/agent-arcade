## Setup

1. Connect an AI in **Connect a companion**. This preview supports local Claude program mode, Claude API, GPT API and DeepSeek API. The character is selected independently of the provider. Local Codex remains available for coding, but companion mode is disabled until an enforceable no-tool App Server configuration is verified.
2. Select QQ and configure its independently logged-in local NapCat bridge and your owner QQ number as described in [QQ setup](QQ.md). Keep the account separate from the owner's ordinary QQ client. Credentials remain in the existing encrypted vault.
3. While disconnected, open **Companion / 相处方式**, enable companion mode and select the original character portrait, name and public persona. Public persona text can be used when generating space posts; keep private details in the separate memory field.
4. Save and connect QQ. The app verifies the actual bridge account and bound contact. Companion mode uses an app-owned empty working directory; it does not need a coding project. **相处 / Together** can then manage that verified relationship's facts, appointments and diary. The older freeform private-notes field remains editable while disconnected.
5. Optionally enable proactive conversation or space posts, and choose contact hours and frequency. These switches default off. They do not ask for a permission code for each ordinary social message. Changes to identity or the bound account pause proactive activity; configure it for that relationship before continuing.

The app must remain running and connected. There is no autonomous service after app exit, automatic reconnection after restart, or catch-up replay of missed activity. Model calls use the selected original account or API billing normally, including calls that decide to wait.

## Conversation pacing and interruption

The current source waits for **1,800 ms** of silence, with a **4-second maximum batch window**, up to eight messages and 2,800 combined characters per batch. Individual incoming messages remain limited to 2,000 characters. This adds 900 ms to the usual single-message wait compared with the original setting. When a new input exceeds the message/character limit, pending old batches are explicitly cancelled and the newest input starts a fresh turn. Actual incoming history is retained; earlier inputs remain available within the existing bounded context. A continuing burst cannot postpone the same batch indefinitely. The four-second bound is the batch-ready deadline, not a promise that an earlier cancelled model or in-flight QQ send has already settled.

Answers use up to four natural paragraphs, with a 450 ms inter-bubble pause. Long unbroken words, code or URLs are not cut just to create another bubble. Each actual send has a durable intent and receipt. An unknown send result stops remaining bubbles without retry. A newer ordinary owner message cancels the old model call and unsent bubbles; already submitted QQ messages cannot be recalled and their receipt may arrive later. Read-only status, memory and follow-up queries preserve ordinary running/buffered replies; explicit stop and memory mutations retain their cancellation behavior. Any owner interaction still interrupts autonomous activity.

The latest source records bounded, body-free companion delivery counts in the existing recovery database: planned, attempted, confirmed accepted, unknown and in-flight bubbles, plus the unattempted/in-flight counts at cancellation. A late receipt for an already in-flight send is distinct from a new attempt. Recovery changes interrupted in-flight counts to unknown and never replays them. Records follow the existing inbound task, 30-day/10,000-row bounds; the latest ten diagnostics expose hashed task IDs, not prompts or reply text. The 53-test targeted checkpoint covers these boundaries and the later 551-test integrated checkpoint includes them. ## How initiative works

The model proposes **wait**, **message**, or **post**. A deterministic controller checks the current connection, active hours, cooldown, recent conversation and daily limits again before an external action. Incoming owner messages interrupt an in-progress proactive decision; ordinary conversation takes priority.

Defaults use this computer's local time: **09:00–22:00**, at least **180 minutes** between considered activities, up to **two proactive messages** and **one post** per day. The character stays quiet for at least **15 minutes** after conversation and does not send a second proactive message until the owner responds. Proactive messages also require owner conversation within the last seven days. A daily limit is a ceiling, not a target.

**Consider activity now** obeys the same rules and can choose to wait. **Pause proactive activity**, `/pause`, `暂停主动`, or `别主动找我了` turn off proactive messages and posts while leaving replies available. `停止` or `/cancel` also cancels the current model reply and clears queued inputs; an already accepted message or post cannot be unsent. `状态` reports the two activity switches.

Compared with a fixed scheduled greeting, this can retain a real previous topic, decline an unnecessary interruption and avoid repeated unanswered messages. Those are implemented control differences; greater naturalness, emotional value and lower interruption cost remain hypotheses for real use.

## Explicit follow-up appointments

An appointment stores its topic, source identifiers where available, due time, IANA time zone, revision and send state in SQLite. The desktop editor displays its time zone; verify that label before saving. QQ also accepts an explicit offset, for example `回访 2026-11-06T18:00:00+11:00 | 聊聊今天的面试`. `查看回访` lists pending entries and `取消回访 CODE` cancels one; desktop buttons avoid entering codes. Vague phrases are not silently promoted into schedules, and model prose alone does not save a reminder.

An agreed appointment may bypass the random-initiative cooldown, 15-minute quiet period and unanswered-initiative barrier. It still requires an enabled companion, connected QQ, proactive messages enabled, the contact window and daily message allowance. After generation, the controller rechecks the saved revision and current policy, then claims the appointment before sending. Changed or cancelled appointments cannot send an old draft. The normal timer checks once per minute; an appointment over five minutes late becomes **missed** rather than sent. Restart also marks already-overdue pending appointments missed. A committed attempt interrupted before its result becomes unknown and is not replayed.

The latest source gives ordinary/private model context up to six recent structured appointment summaries, including current state and due time, to distinguish cancelled appointments from older creation messages. Summaries omit authority IDs and receipts and are capped at 800 characters and one quarter of the context budget. Public drafts/posts still have no private appointment context. This prompt correction and accurate policy-limited proactive-capability wording passed 54 targeted checks after the reviewed package was built; they are not yet loaded in that running package or live-accepted.

## Conversation memory and tools

`social-memory.sqlite` stores the most recent **120 messages per verified account/contact/character**, up to **1,000 characters of owner-edited notes**, and up to **100 explicit long-term facts**, each at most 600 characters. Facts retain source/time and revision; desktop entries are labelled manual. QQ commands include `记住：内容`, `查看记忆`, `更正 CODE：内容` and `忘记 CODE`; desktop actions avoid codes. No model-generated biography or inferred relationship fact is automatically promoted into permanent memory.

Model prompts receive bounded recent context, notes and selected recent facts: at most 30 recent messages, a total 6,000-character prompt bound, and a default 3,000-character context allowance for random initiative. Large descriptions/current messages leave less room for history. Durable storage does not guarantee that every fact is retrieved on every turn; this revision has no semantic search, embedding service or automatic memory extractor. Relevant context is sent to the selected model. Local text storage is separate from the metadata-only recovery journal.

Names are limited to 40 characters and public persona descriptions to 800. Incoming companion messages are limited to 2,000 characters. Storage allows at most 20 relationship scopes and 200 recent action records per scope. Old ordinary-reply receipts are pruned first; recent initiative records remain available for daily limits.

Correcting or forgetting a fact stops and settles older model/send activity, clears retained controller task text, clears this relationship's recent conversation and freeform notes, removes exact duplicate facts and clears/cancels dependent follow-ups. Independent structured facts remain. Clearing the broader conversation prevents earlier mentions or paraphrases from immediately recreating a forgotten value; the UI explains this deliberate data-loss tradeoff.

Disconnect before clearing all memory. Clearing deletes this relationship's messages, notes and facts, clears follow-up text and pauses proactive activity. Minimal action IDs, times, states and receipts remain to preserve limits and uncertain-send history. Public journal entries remain separate. Neither operation deletes QQ messages, space posts, provider-side records or backups.

Companion model runners have no file, shell or account-operation tools. Claude uses a replacement system prompt, safe mode, an empty tool set, all-tool denial, strict empty MCP configuration and no session persistence; it does not resume a coding session. Claude API, GPT API and DeepSeek similarly receive no tools and reject unexpected tool calls. Social account actions belong to the application controller, not a model permission bypass. Switch back to coding mode to request local work.

## QQ space and delivery evidence

The adapter targets NapCat **4.18.42**. Proactive private messages are a distinct transport path that verifies the signed-in account and allows only the bound owner; it does not fabricate an inbound reply token.

Space publication uses `send_qzone_msg` with explicit selected-friend visibility (`ugc_right: 16`, `target_uins: [owner]`), never NapCat's public default. The adapter also supports self-only publication (`ugc_right: 64`); the companion controller requests the bound-owner audience. A fresh model call generates the post from the public persona and a bounded selection of previously accepted public journal entries, without private chat, facts, notes or a resumed model session. A local draft is not public continuity until the interface accepts publication. This is text-only: no photos, social-feed browsing, comments or likes.

The journal page can generate a draft, save/edit its exact text, then explicitly publish it. QQ also accepts `发布说说：正文`. This explicit action does not require the autonomous-post switch, active window, quiet period or random-initiative cooldown; it still requires a connected, idle companion, healthy storage and the configured daily post allowance. A zero daily allowance prevents explicit publication too. Drafts are claimed once before sending, and uncertain entries cannot be republished automatically. Deleting a local entry does not remove the external QQ-space post.

Send intent is committed before the network write. An ambiguous result is recorded as `unknown` and is never automatically retried. Restart marks an unfinished send intent unknown. A bridge message ID or post ID means **the interface accepted the request**, not that a person received it or the audience restriction worked. Post content is read back separately. NapCat's current detail parser does not preserve the audience fields, so content verification leaves `visibilityVerified: false`. Real audience acceptance requires the owner to see the exact post and a controlled account outside the whitelist to receive an explicit access denial while the owner can still see it; a network error or empty list is not exclusion evidence.
