# Remote cleanup of a previous QQ run

This extension is optional and separate from ordinary Start, Stop and Recover.
The host administrator enables `recovery.orphanCleanup` for one declared managed
Shell installation. It uses the supervisor's independent HTTPS credential;
existing model, QQ and WebUI credentials are unchanged.

## Use

Open **QQ accounts → Remote instances → selected registration → Remote QQ
process → Settle the previous run**. The section stays in the existing window
and uses the original font sizes and mist-pink controls.

1. Connect to the saved supervisor and explicitly inspect the previous run.
2. Read the offered action. It can describe either a verified former process
   tree or resources retained by an incomplete inspection. These are different
   kinds of authority; an unavailable process observation is not zero processes.
3. Preview that exact action, then confirm once or choose **Not now**. A stale
   or expired preview needs a fresh inspection. Cancel discards that ticket.
4. Read process absence, management-record settlement and resource closure as
   separate results. A partial effect remains unresolved. Refreshing or starting
   QQ later is a separate explicit action.

Resource-only settlement closes the resources retained by that inspection.
It does not stop a process or remove account records or update plans. Process
cleanup uses the existing precise local ownership rules; it cannot select an
arbitrary program, path or account. Neither operation connects AI or proves QQ
login, message delivery or task success.

## Lost responses and restart

The service records each request before invoking its effect. The desktop saves
the matching pending request in its encrypted supervisor registration. After a
lost response or restart, use **Query original operation**. The same request ID
does not perform cleanup again. A missing result after a possible send remains
unknown; it is not evidence that nothing happened.

Closing the page retires its local preview and connection. A submitted server
operation can still finish. **Not now** explicitly discards an unsubmitted
ticket; closing the window is not a promise of remote cancellation. The original
bounded unknown-receipt retention flow remains available without relabelling an
unknown result as success.

The server's orphan ledger was introduced in SQLite schema v4 and is retained
when native Passkey maintenance upgrades it to v5. Request IDs and capacity are
shared across operation families. Disabling the feature does not erase its
ledger or authorize a replay.

## Supported boundary and evidence

The adapter supports the typed pending-installation and inspection-resource
protocols, plus the fixed healthy managed Shell 4.18.42 path. The latter reuses
the existing local ownership proof and stop implementation; its private service
ticket supplies a 60-second expiry. It does not claim that the older local preview
had a persistent ticket. Only the recorded, rechecked former child processes are
selected. Account data is retained and QQ never starts automatically.

Healthy results separate verified process absence, removal of the original
ownership record, and operation-resource closure. If the original guard remains
after the process effect, the result stays partial/unknown. Do not retry the old
cleanup or remove that guard manually based on this receipt. Have the host
administrator inspect the retained record; this extension does not add a repair
action for that legacy guard. This is not remote installation, component repair
or automatic reconnection.

### Update both sides for the healthy path

The orphan extension now uses protocol **/2**. Update both the desktop app and
the separately deployed supervisor. Ordinary process management still uses its
existing protocol. A version mismatch blocks orphan previews and queries with a
clear update message; it does not change credentials or erase a pending request.

If an earlier request is unresolved, keep its encrypted desktop registration and
the supervisor state directory. After updating both sides, use **Query original
operation**. Existing pending-installation and inspection-resource receipts remain
readable; query never invokes cleanup again. The SQLite schema is unchanged by
this protocol update. Downgrade to an older binary after writing a healthy receipt
is unsupported because it cannot interpret the new result kind.

### Validation boundary for the healthy path

The healthy protocol tests use private temporary files, the production ownership
methods and an explicitly synthetic process host. A local HTTPS/SQLite/client
flow verifies duplicate/query behavior and stored v1 receipt compatibility. The
same-window renderer checks cover the actual main handler/panel/client/service
chain, known and partial results, version mismatch and retained pending requests.
These component checks do not verify native process termination, user QQ recovery
or an actual remote host. Those remain separate acceptance gates.

The work-only component checks exercised real local HTTPS and SQLite, temporary
Windows files and synthetic QQ observations. The renderer checks covered the
actual main-handler/controller/client chain in the same-window panel. They are
separate from native process acceptance and actual user QQ acceptance.

A separate isolated Windows run exercised Client → HTTPS → adapter → production
runtime against a private inert process tree. It confirmed only the original
recorded child was stopped, while an unrelated control process, update marker,
component lock and account data remained unchanged. A duplicate confirmation
and original-operation query caused no further stops. All four private process
identities were independently absent after observer cleanup. One imported but
uncalled desktop Panel file changed during that run. The captured service,
client and runtime inputs were stable, but the captured list omitted some new
overlay-only modules. These facts do not constitute a complete dependency
freeze, a final-build check, a real remote-host deployment or QQ login verification.

Production integration, packaged operation and current acceptance are tracked in
[the delivery scope](ACTIVE_GOAL.md). Real remote inspection, cleanup and account
reconnection remain unaccepted until performed against the intended deployment.
