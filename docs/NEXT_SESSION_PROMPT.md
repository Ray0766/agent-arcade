二、开发模型与工作方式

建议主模型使用 GPT-6.1 Sol，思考程度 High。复杂架构、跨平台进程、数据库迁移或反复定位不出的故障，可使用 GPT-6 Astra＋Extra High 做专项分析或审查。实际模型以客户端可用选项和当前设置为准，不声称仅凭提示词已切换模型。

可合理分派 agent 并行处理互不冲突的任务，由主 agent 负责整合、审查和端到端验证。明确文件归属，避免多个 agent 同时修改同一处代码。

能自行完成的实现、运行、验证和修复直接做，不停在计划、第一版或阶段汇报后等待我说“继续”。确需我的凭据、真人操作、设计决定或额外授权时再集中提出，同时推进不依赖这些条件的部分。

优先使用代码、命令行、测试工具和隔离自动化验证，本轮不使用 Computer Use。避免重复全量测试、无收益的反复检查、不断扩展抽象或新增无关功能。

三、产品方向与范围

目标是：用户下载一个 App，配置一个 AI API key，就能直接在 App 内与有稳定人设和连续记忆的角色聊天。

沿用 Electron 和现有角色、后端、渠道分离架构。项目按最新 AGENTS.md 保持 AGPL-3.0 完全开源，不设收费功能。

界面遵循最新定案：

- 三种布局：沉浸式默认、聊天应用式、极简工具式。
- 主题色默认跟随角色，也可自定义。
- 分为“陪伴”和“工作”两个工作区。
- 保留日间、夜间、跟随系统。
- 保留原创角色资产和品牌标志。

不要恢复旧版雾粉布局、花枝点缀或原字号等已经被新定案取代的约束。

普通 QQ 仅保留既有可选能力，不扩展新管理功能，不继续独立 QQ 核心实验，不将 QQ 登录作为 App 聊天的前提。必要时修复本轮改动造成的既有功能回归，但不要重新启动历史 QQ 开发计划。

四、完整缺口清单与实施要求

先根据最新文档、真实代码和验证记录建立一份完整且可追踪的缺口清单，逐项标明：

- 已实现且有对应验证；
- 已实现但尚未完成真实验收；
- 尚未实现；
- 因外部前提暂时无法完成。

每项写清使用入口、预期行为、完成条件和证据。所有仍有效、已确定的功能缺口都要纳入；优先级只决定先后，不缩减交付范围。历史上已经取消、替代或暂停的范围不自动恢复。

优先核实并补齐以下已知问题；如果当前代码已修复，则验证并更新记录：

1. 内置角色的 App 对话接入已批准的共享笔记和规则。
   保持逐条批准、每角色可读／可提议开关默认关闭、私有记忆隔离及上下文预算。不能把未批准的候选直接当作生效规则。

2. 任务看板补齐历史结束任务的查看、管理与明确清理，以及返工要求实际进入执行流程。
   每任务独立 git worktree；遵守 AGENTS.md 对 worktree 内文件修改的预授权边界。防止重复执行和越界。交回不等于完成，完成仍须主人验收。

3. 修复笔记检索噪声、内置角色空对话起步体验，以及与新界面不一致的实际入口和测试脚本。

4. 跑通 App 首次使用：

候选方向是：

后续正式启动时，先完成一位角色的完整流程，再按统一规范覆盖其余角色。验收应包括：

- 可编辑源文件、贴图、服装配饰及素材许可；

- 保留静态立绘回退。

生成效果图不能代替可用模型，模型能显示不能代替绑定、动画和应用接入完成。

七、验证与交付

验证对应实际用途和主要风险，优先端到端闭环：
真实输入 → 处理 → 输出 → 停止／失败 → 重启恢复。

明确区分：

- 源码实现；
- 单元／组件测试；
- 隔离界面验证；
- 真实模型、真实数据源与真实操作系统验收。

构建通过、测试替身和截图不能替代相应真实流程。不要为了制造通过而修改用户正常使用节奏、掩盖未知状态或降低验收标准。

保护真实密钥、聊天记录、记忆、账号配置和私人验收文件。未经本轮明确要求，不提交、推送、发布或更改仓库可见性。

持续更新 WORK_LOG.md、docs/HANDOFF.md 和当前范围记录，保留关键决定、修改文件、验证命令、证据位置、失败原因及剩余限制。最终按缺口清单逐项交付使用入口、完成状态和证据；缺少前提或尚未验收的项目明确标为未完成。

核心体验始终是：同一个角色能延续之前的话题，记住用户明确希望保留的事，在合适的时候回应，并让用户能理解和控制这些行为。先把已定案的体验做完整，再提出新增功能建议；建议不自动成为开发范围。
