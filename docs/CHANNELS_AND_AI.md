# Channels, AI backends and characters

Updated 2026-11-08 for the single-window, multiple-companion application. Source availability, a configured connection and real acceptance are recorded separately below; a planned catalog entry is not an integration.

## Current implementation

One main window manages multiple independently configured companions. A messaging route binds one channel, one backend and one allowed private sender; coding mode also requires a selected local project. Changing that route requires disconnecting it. The separate **App conversation** uses saved AI access without a channel, QQ login or selected project folder, and keeps local history and memory isolated from QQ. It can coexist with the channel route; stopping App chat does not disconnect QQ. See [App conversation](DESKTOP_CHAT.md). Provider keys remain separate and are never passed to a different provider. The SQLite receipt namespace separates QQ account/owner identities from WeChat and suppresses the same incoming message even after a backend switch. See [account isolation and real companion evidence](COMPANION_ACCEPTANCE.md).

**Current bindings:** Ju/orange uses Claude API, Dragon Girl uses GPT API and Whale Girl uses DeepSeek API, following the owner's later choices. Local Claude program mode and local Codex remain available. The former temporary three-application arrangement has been replaced by one main process/window with isolated companion services; QQ runtimes remain separate background processes. Existing QQ installations can be managed inside the app. The optional complete Node runtime passed one actual create/select/configure/start/QR/stop/return flow. Authentication, messaging and clean-machine setup remain unaccepted. [Management and capability inventory](QQ_INTEGRATION.md), [Node setup limits](QQ_NODE_SETUP.md).

## Separate identities

- **Channel:** where messages enter and leave. Each real connection needs its own credentials, owner/access rules, delivery identifiers and capability declarations.
- **Backend:** what runs the work. Local Claude Code and Codex are execution tools; a model API alone does not supply tools, filesystem access or task cancellation. Every added API needs an actual runner and explicit permission/state mapping.
- **Character:** name, portrait and an optional light conversational tone. The AI-specific defaults and Sprout alternative are recorded in [PERSONAS.md](PERSONAS.md). The separate anime/pixel appearance choice stays cosmetic. Explicit character/tone settings apply to the next connection through fixed style instructions; they never change execution authority or connect a planned backend.
- **Binding:** a channel route binds channel connection + allowed sender + backend session + character, plus workspace for coding. The independent App route binds the companion service and character to a separate local conversation scope, without inventing a QQ identity or copying QQ memory. Multiple routes use separate account services, vaults and conversation identity namespaces. Do not route by display name or share one platform's approval code across channels.

Implementation availability, live connection state and verification evidence are separate facts. A returned message does not establish that work succeeded; a requested cancellation does not prove the independent process stopped.

## Bothouse reference and reuse decision

Read-only review of local Bothouse commit `920f176b281399490a6c966a29ea90341b577bf3` found independent platform and agent interfaces and an authenticated WebSocket Bridge Protocol for external adapters. Its role/backend separation is an appropriate model for the catalog. Its anime portraits were visually inspected; new Agent Arcade artwork was generated independently because the avatar source notes alone did not establish redistribution rights. See [UI_REFERENCES.md](UI_REFERENCES.md).

A future optional Bothouse bridge could reuse existing adapters, but it would introduce another process, installation/update lifecycle, authentication and session semantics. Its documented automatic permission defaults must not silently replace this app's explicit boundaries. Copying Apache-2.0 code also requires its license and applicable notices. The current revision adds no Bothouse dependency, process, credentials or integration.

QQ now uses a direct OneBot transport adapter, without a Bothouse runtime dependency. Its local structured-event tests cover authentication, sender/account identity, reconnect and duplicates; no comparative setup-cost, performance or usability advantage has been measured. A real-account comparison remains unaccepted.
