# Recover an existing managed Shell process

Prepared candidate: `single-window-supervisor-owner-ntfs-20261107`, 2026-11-07.
The currently operated application has not been replaced or restarted. See the
[current delivery scope](ACTIVE_GOAL.md) for the package and acceptance record.

## What this resolves

A pending component update or interrupted update record must prevent another
QQ startup. It should not by itself prevent stopping an already owned process,
or explicitly recovering a previous manager's verified process. These are
different capabilities. A running launcher does not establish QQ sign-in or
an AI connection.

This path applies only to the fixed, prepared managed Shell installation. The
original startup must have captured the new installation-bound ownership record.
It does not manufacture that evidence from an old record after a failure. Node,
ordinary QQ and other installations do not acquire this recovery authority.

## Existing entrances

In **QQ accounts**, open the account details and use **More → Stop QQ**, or
the existing **Recover management** primary action when offered. The pending-update explanation
continues to block startup. Recovering a fully stopped record removes only the
proved obsolete management record; recovering a complete surviving tree adopts
that tree without starting QQ. Recovered management does not confirm login.

For an explicitly configured remote supervisor, use **QQ accounts → Remote
instances → Remote QQ process** and the existing preview and confirmation.
The service and desktop must contain this implementation. The service's fixed
account, credential, operation ledger and original observation binding remain
in force. This adds no arbitrary executable, command, path or account selector.

Stopping or recovering an account does not remove an updater plan, component
lock or interrupted transaction. Those retain their separate
[plan recovery](QQ_SUPERVISOR_RECOVERY.md) and
[orphan-lock recovery](QQ_SUPERVISOR_LOCK_RECOVERY.md) entrances and permissions.
The account can therefore be safely stopped while startup remains unavailable.

## What is verified before changing a process

Private ownership records bind the original installation, selected component,
configuration and data directories, executable evidence and runtime tree.
Process checks include process ID, creation time, executable and parent chain.
Cross-manager recovery additionally requires the previous manager to be absent.
Replacing a record or directory, reusing a process ID, an unknown descendant or
incomplete process tree must not silently grant control.

The recovery path does not require component bytes currently on disk to be
usable for a fresh startup. Their startup evidence is retained, while current
installation and process identity checks still apply. This is not permission to
run altered code. A new startup continues through ordinary component validation.

Closure has its own result: an empty run list cannot prove all guard handles or
coordination resources closed. Failed cleanup retains its owner for an explicit
retry. A missing response remains unknown, and is never automatically replayed.

## Validation and remaining limits

The preceding full regression passed 3,873 checks, with one existing opt-in skip and zero
failures in 197,848.7823 ms. It includes the seven actual inert-process cases.
The first full run found an inherited Node version-2 dispatch regression; its
failed log and candidate are retained. The narrow engine-specific correction
passed 492 adjacent checks before the successful full run. Existing Node
source and test assertions were not changed to hide that failure.

The separate service then exposed an actual NTFS publication error during
Start → Stop → Start. Windows restored the old destination's creation time even
though the new file ID and complete bytes remained unchanged. Publication now
keeps the original exclusive file handle through rename and verifies that held
file against the named destination. Ordinary identity checks remain strict;
same-byte replacement by a foreign file is rejected. A reported rename error
is treated as applied only when independent readback proves that exact result.
The correction passed 496 adjacent checks and all 58 separate service checks.

The first full run on this correction passed 3,876 checks with one original skip
and one failure: the existing real crash/reconciliation test reported
`process_check_failed`. Its isolated instrumented repeat passed with successful
Windows queries and unchanged production timeouts. The original cause remains
unknown; that failure is retained, rather than described as fixed by a retry.
A separate standard full confirmation passed 3,877 checks, one original opt-in
skip and zero failures in 219,488.9998 ms. All seven native cases ran on that
fixed source and independently confirmed the 20 created process identities
absent. This later result does not explain or erase the earlier refusal.

The production renderer/main/local HTTPS flow passed eight checks with 12
inspected images on unchanged final UI files. Its native flow uses original
inert programs; local capability rows and the cleanup-error projection are
separately marked synthetic. Source/package comparison matched all 321 source
files and the approved voice. These are isolated acceptance results, not a new
packaged desktop smoke or an actual user-account recovery.

The native test programs are original inert executables, with no QQ protocol,
real account or model request. A production-start preflight followed by an
abnormal manager exit did not retain the entire launcher/child tree. A separately
labelled detached test launch can exercise surviving-tree recovery; that launch
option does not establish the lifetime of normal production QQ processes.
The incomplete tree is rejected with its ownership record retained. Test-only
termination of that leftover child is not an implemented product cleanup flow.

The original pending-update helper also produced actual two-link marker/plan
and intent/pending records. After temporary relocation allowed ordinary startup,
the same inodes were returned to simulate their later arrival. Verified Stop
preserved all four files, bytes, identities and link counts. This does not claim
that the helper itself is allowed to create these records while QQ is running.

Old ownership records are not automatically upgraded. A crash after spawning
but before recording durable runtime proof remains unresolved. Actual user
installation recovery, remote-host operation, QQ login stability and the
deferred human acceptance gates are not established by isolated tests.

Existing encrypted Claude, GPT and DeepSeek keys are retained. This feature
does not need or replace model credentials.
