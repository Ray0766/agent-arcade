# Personal QQ account channel

For the current single-window workflow, see [Start and connect a saved QQ
companion](QQ_START_CONNECT.md) and [QQ management](QQ_INTEGRATION.md). Saved,
readable API keys do not need re-entry. The dated setup and acceptance records
below retain their historical scope.

Local/source implementation, 2026-11-04. This channel connects an independently logged-in **ordinary QQ account** through a local OneBot v11 bridge. It is not a Tencent official QQ robot application and does not create a QQ account. The account can be added as a normal friend in QQ; the owner handles login and friend requests in the QQ client or bridge.

This integration accepts text from **one explicitly configured owner in friend private chat**. A separate source implementation lets the user explicitly select and preview a local PNG/JPEG before sending it to that owner; see [manual images](QQ_MEDIA.md) for its pending real acceptance and privacy limits. Incoming attachments/voice, group conversations, temporary group chats, other friends, automatic friend acceptance and public multi-user agent hosting are not implemented. A matching account identity or accepted API send is not proof that the human received a message or that an agent task succeeded.

## Connect an existing local bridge

1. Prepare a separately controlled QQ account for the AI and add it as a friend from the owner's QQ account. Agent Arcade never requests the QQ password, login cookies or registration details.
2. In Agent Arcade select **QQ → Open NapCat download page**. Independently install and log in to a compatible OneBot v11 bridge. The fixed link opens [NapCat Desktop's release page](https://github.com/NapNeko/NapCatQQ-Desktop/releases/latest); **Connection guide** opens its [forward WebSocket instructions](https://napneko.github.io/NapCatQQ-Desktop/docs/connections/). Agent Arcade does not bundle, install, modify or start NapCat/QQ. Review that project's current terms and compatibility before using it.
3. In the bridge's network configuration, enable a **WebSocket server / forward WebSocket** with a loopback host, an explicit port, an access token and array-form message reports. For the example address below, use host `127.0.0.1`, port `3001`, message format `array`, self-message reporting off and a 30-second heartbeat. The WebSocket service port is different from the bridge's management WebUI port. These settings correspond to the [NapCat configuration guide](https://napneko.github.io/config/basic).
4. Use **Prepare token**, then **Copy token** to paste it into NapCat's OneBot token field. Preparing again preserves an existing token. In NapCat Desktop select **Universal (API + events)**, root path `/`, save the connection and save the bot configuration. Its WebUI password is a separate credential. Alternatively, **Copy NapCat config** copies one `network.websocketServers[]` entry for a compatible NapCat configuration editor; it is not an entire config file or a Desktop import file. Do not replace existing connections with this fragment. It contains the secret token, so do not share it. TLS connections require manual certificate configuration; their token can still be copied.
5. In Agent Arcade enter the **owner's QQ number**, not the AI account number, and save. The default address is `ws://127.0.0.1:3001/`; advanced settings allow another local port and an existing OneBot token (16–256 visible ASCII characters without spaces).
6. Click **Test connection**. No project, AI login or API key is needed for this read-only check. It displays the actual AI QQ number/nickname, QQ online status and whether the owner is a friend. Unknown is kept separate from false. If needed, add that number from the owner's QQ and manually accept the friend request on the AI account. Test again after login/configuration changes.
7. Choose an AI backend and project, then **Start receiving tasks**. Starting rechecks the account and refuses explicitly offline/not-friend results. Wait for the connected state and one second, then send a new text message from the owner. Older/offline messages are not fetched. OneBot event times have second precision, so the first partial second after connecting is conservatively excluded.

Only numeric loopback addresses (`127.0.0.1` and `::1`) with an explicit port and root path are accepted. The token travels in the `Authorization: Bearer` header, never a URL query. The app does not accept a public bridge URL, redirects or a WebUI URL. Existing credentials are saved through the app's OS-encrypted vault, not renderer snapshots.

The test calls only `get_login_info`, `get_status` and `get_friend_list`, then closes its connection; it never starts an AI or forwards queued events. The friend list is bounded, reduced to an owner-membership boolean and discarded. It does not enter the snapshot, journal or logs. If an optional API is unsupported or malformed, that result is **unverified**, not success. Test results are in memory only, invalidated by QQ connection-setting changes, and never restored after restart. Checking times out after 15 seconds; disconnect cancels it. A successful check establishes bridge/account metadata, not a completed human chat round trip.

## Message and recovery rules

- Ordinary text goes to the selected backend. The bridge sends replies as explicit text segments, so text resembling a CQ code cannot become an image, mention or other action.
- A text reply can contain an array-format `reply` segment. Only its referenced message ID is included as unverified context; this integration does not fetch old messages. Quoted control/approval commands are rejected. Send controls as fresh, directly typed text.
- A message containing images, files, voice or unsupported segments is rejected as a whole. Its remaining text is never silently submitted as a task. The app returns a short explanation to the owner.
- Only current friend-private events from the configured owner and logged-in AI account are considered. Other senders, group events, self echoes and old/duplicate IDs are ignored. The setup/connection check queries the friend list only to confirm the owner. The app never reads account cookies or automatically accepts invitations.
- A broken connection rejects pending sends and discards undelivered local events. The service can reconnect, but it does not resend an ambiguous send, replay a task or reuse an old reply context. A different logged-in account is rejected until a new explicit connection is configured; an identity change reported by an event or heartbeat on an existing socket also revokes that connection and its contexts. Existing task state must not be described as verified delivery.
- Receive frames are bounded to 1 MiB, the pending event queue to 200, the instance's seen-message IDs to 10,000 and outstanding bridge requests to 20. Overflow fails closed instead of losing the deduplication guarantee. The transport uses a bounded handshake/action timeout and liveness checks.

## Why this path, and how it differs from WeChat

The user requires an AI with its own normal account that can be added as a friend. Tencent's [QQ robot documentation](https://github.com/tencent-connect/bot-docs/blob/main/docs/README.md) describes creating and configuring robot applications; that is a different identity model. The OneBot protocol separates the already logged-in account bridge from the agent and offers structured events, authentication and request correlation. The benefit over screen scraping is that sender IDs, message IDs and send receipts are structured. It does **not** make a third-party bridge official or guarantee continued platform access.

The current WeChat channel remains Tencent's [iLink/ClawBot integration](https://github.com/Tencent/openclaw-weixin). That documented message channel is not evidence of an API for operating an arbitrary ordinary personal WeChat account. This QQ implementation therefore does not silently change WeChat into personal-account automation or claim that anyone can add the existing ClawBot as an ordinary friend. Personal WeChat access requires its own implementation and acceptance decision.

Protocol implementation was written against the [OneBot v11 WebSocket specification](https://github.com/botuniverse/onebot-11/blob/master/communication/ws.md), [authentication specification](https://github.com/botuniverse/onebot-11/blob/master/communication/authorization.md), [private-message events](https://github.com/botuniverse/onebot-11/blob/master/event/message.md) and [public API definitions](https://github.com/botuniverse/onebot-11/blob/master/api/public.md), checked 2026-11-04. It uses the existing Node environment plus the locked `ws` package. No bridge source is incorporated. NapCat currently has a [Limited Redistribution License](https://github.com/NapNeko/NapCatQQ/blob/main/LICENSE) and mixed third-party licensing; it must not be described as an MIT dependency of Agent Arcade.


## Local Claude startup is separate from QQ login

QQ account login, NapCat WebUI administration login and the original Claude Code login are different states. An online QQ bridge does not prove its selected AI session is ready. Local Codex uses App Server and DeepSeek uses its saved API credential. The owner now selected [Local Claude · program mode](CLAUDE_PROGRAM.md) for Ju: it directly runs the original CLI through structured input/output without loading Channels. The older interactive Channels route remains selectable.

For the legacy route, the [official Channels reference](https://code.claude.com/docs/en/channels-reference#test-during-the-research-preview), checked 2026-11-04, requires a development-channel startup confirmation in an interactive session. Passing the flag to print mode or Agent SDK does not register the channel. Keeping the same Claude session open avoids repeating this startup step for each message; it does not remove tool permissions.

The legacy Channels UI distinguishes an opened Claude process awaiting a channel from a CLI that has not been opened. The app renews the startup connection lease only while it verifies its own running process, preventing the previous five-minute waiting timeout from closing that process. The attached heartbeat timeout, explicit stop/disconnect and no-replay rules remain. This is a startup reliability fix, not persistent unattended Claude hosting or evidence of a QQ-to-Claude round trip.
