# Architecture and accuracy

## Current source: messaging and execution adapters

`AccountManager` manages up to six independent companion profiles in one Electron main window. Each profile's `BotService` selects one channel (`wechat`, `qq`, `feishu`, `x` or `messenger`), backend (`claude`, `api`, `native`, `codex`, `gpt`, `deepseek`, `gemini` or `doubao`), project and allowed private sender. Availability and real acceptance differ by route; the lists are source capabilities, not a promise that every combination is supported. Switching that profile's channel/backend requires disconnection; other companions can remain connected. Exact account claims prevent two profiles from consuming the same QQ identity. The OS-encrypted vault keeps each provider key and channel credential in separate fields; renderer snapshots expose presence flags and non-secret settings only. The selected runner receives only its provider's key; local Claude program mode and Codex do not receive an API key. Saving another backend's key preserves the existing keys.

- **WeChat** retains its official iLink/ClawBot transport. It is not ordinary personal-WeChat-account automation.
- **QQ** uses an external local OneBot v11 bridge for an ordinary QQ account. The single-window manager can start/stop an existing component installation, show its login QR, manage connection bindings and inspect account state. The app connects only to a literal loopback WebSocket address with a bearer token, verifies actual account/online state, and accepts fresh friend-private messages from the configured owner. Event/heartbeat account changes revoke the connection and reply contexts; directory listing does not enable group or arbitrary-friend tasks. Text and explicitly selected owner media use correlated receipts, with no automatic ambiguous-send retry. NapCat/QQ are not bundled: optional verified component staging is an explicit download, not a fresh QQ installer. [QQ contract](QQ.md) · [management and evidence](QQ_INTEGRATION.md).
- **Local Claude program mode** (`claude`) controls a separately installed original `claude -p` process through its structured protocol, retaining original CLI sign-in without copying credentials or loading a custom Channel. Coding tools use the dispatcher approval contract; companion calls disable tools and use their separately bounded context. Legacy `native` Channels is a different compatibility route. [Program-mode contract](CLAUDE_PROGRAM.md).
- **Local Codex** starts an owned original-CLI App Server process per turn, uses structured account/thread/turn events, resumes only the explicit thread ID within a connection and handles approval requests through the existing dispatcher. Native workspace-write/on-request permission settings apply; ordinary permitted workspace actions need no new chat approval. Stop requests interrupt the exact turn and wait for its completion event. [Codex contract and direct real evidence](CODEX.md).
- **DeepSeek API** uses the fixed HTTPS Chat Completions endpoint through Node fetch and a bounded sequential tool loop. Approved Read/Write/Edit/List operations use explicit path/content checks; there is no shell tool or dollar-cost limit. History remains in memory for the connection and is not reconstructed from the receipt ledger. [DeepSeek contract](DEEPSEEK.md).

- **GPT API** uses a fixed OpenAI Responses endpoint and separate API key, with stateless in-memory continuation and strict local function tools. GPT and DeepSeek share the approved file implementation, while keeping their provider protocols and histories separate. [GPT contract](GPT.md).

- **Gemini and Doubao/Ark APIs** use separate encrypted keys, fixed provider endpoints/model selections and bounded native response parsing. Task mode uses the approved file interface; companion calls expose no execution tools. Their source/fixture checks do not establish actual provider access or messaging delivery. [Gemini](GEMINI.md) · [Doubao](DOUBAO.md).
- **Feishu** uses the official long-connection client for an enterprise self-built bot, scoped to the configured application's owner ID. **X** uses a distinct user token for standard DMs. **Messenger** uses Page credentials and a separate HTTPS webhook relay with a persistent SQLite inbox. Its signed inbound timestamp bounds ordinary replies; a relay pull or reconnect does not renew that response window. These adapters retain identity checks, deduplication, explicit opt-out where supported and unknown-send handling. They do not provide ordinary personal Feishu/Facebook accounts or encrypted X Chat. Real provider credentials, platform approvals and end-to-end acceptance remain pending. [Feishu](FEISHU.md) · [X](X.md) · [Messenger](MESSENGER.md).

In coding mode, local Claude program mode, Claude API, Codex, GPT, DeepSeek, Gemini and Doubao share the serial `Dispatcher`, one active task plus three queued tasks, owner permission/question handling and a reply-ended outcome. Local Claude Channels retains its distinct broker/session behavior and channel restrictions. The separate QQ `SocialCompanion` controller provides tool-free chat, bounded memory/follow-up context, input batching and interruptible bubbles; local Codex is not enabled for that companion path. Disconnect aborts and joins the current runner before closing its transport; neither model completion nor an accepted messaging send becomes verified task success.

The SQLite deduplication key separates QQ account/owner identity from WeChat and does not include the selected backend, preventing an old incoming message from becoming a new task after switching AI. Real QQ companion chat has bounded evidence for Claude API, GPT API and DeepSeek, including three profiles in one application; this does not accept their corresponding coding/file flows. Claude program-mode coding has separate bounded QQ/ClawBot evidence. Direct real Codex chat, write/resume and interruption remain separate from messaging acceptance. [Current evidence](VALIDATION.md) · [nine-feature ledger](COMPANION_ACCEPTANCE.md).

## Source revision: evidence, recovery and artifacts

The current source adds [six capabilities](TECHNOLOGY_IMPLEMENTATION.md) after the published preview.2 baseline below. `Workbench` coordinates explicit native directory/file pickers, scoped official CLI session checks, app-owned background lifecycle and a local MCP artifact service. JSON observations annotate hooks without replacing them. Background jobs have exact durable ownership and remain separate from messaging execution. Only the legacy Channels route requires its original interactive terminal; WeChat program mode does not.

`BotService` normalizes supplied voice text/quoted context before backend dispatch. A `node:sqlite` receipt ledger commits metadata before dispatch, survives duplicate delivery across restart, expires old permissions and marks interrupted work unknown. This ledger does not retain transcripts, replay input or restore a model session. Companion conversation/fact/follow-up storage is separate and scoped to the actual account, owner and character; published journal context excludes private chat/facts. Current app-owned Channels supports process stopping and explicit same-UUID recovery; program mode does not automatically resume its model session after restart. The released pause-only behavior below is historical. See [recovery details](WECHAT_RECOVERY.md) and [companion storage](COMPANION.md).

The renderer hosts only the bundled MCP App in an opaque-origin, script-only sandbox iframe. Its exact script hash is allowed by CSP; network, parent DOM and tool/message/link delegation are unavailable. Selected file content is literal text, never executable HTML. MCP Tasks belong to bounded local artifact inspection, not Claude execution; they expire in memory after 60 seconds.

## Released baseline: WeChat API and local CLI (0.3.0-preview.2)

This section and the following API subsection describe that historical release. Current entry points and later acceptance are summarized above; do not apply the old terminal, cancellation or pending-test statements to every current backend.

The released baseline's two modes use the same paired-owner WeChat text client, project selection, encrypted WeChat credential and isolated renderer. Its `bot-config.json` selects `api` (default) or `native`; switching requires disconnection and retains the saved API key. Only the selected mode consumes the connection. Neither mode is an OS sandbox. The current source extends this configuration as described above; this subsection preserves the earlier release's behavior.

**Local mode:** WeChat long poll → owner-filtered text → Electron's authenticated loopback broker → Node stdio MCP Channel → the user's original interactive Claude Code CLI. Replies return through a bound `reply(id, text)` tool; native permission prompts use the official channel relay. Claude owns its login, configuration and execution. Agent Arcade neither reads/copies Claude credentials nor sets an API key for the native session.

The broker binds only `127.0.0.1` on a random port. A per-connection 256-bit capability is written to a private MCP launch file, not to the renderer or copied command. Attachment returns a separate client ID; later requests bind to it. One long poll, bounded event batches/history, explicit sequence-gap failure and close-time revocation prevent silent cross-connection reuse. A current message ID is required for replies. MCP write failures close the relay rather than automatically replaying possibly delivered input. Another process running as the same OS user is outside this boundary.

The generated command starts the installed Node.js 22.13+ channel through original Claude Code 2.1.317+ with `--allowedTools mcp__agent-arcade-wechat__reply --permission-mode default`, a private strict MCP config and the custom development-channel flag. Only the exact reply tool is pre-allowed for this session; deny/ask rules, hooks and organization policy still apply. There is no general permission bypass or permanent setting change. The user must personally confirm the research preview/project/MCP prompts and keep the CLI session open. Runtime files/dependencies are unpacked from ASAR for system Node. The launch capability is revoked and its file is removed on disconnect where possible; a leftover file cannot authenticate to the closed broker.

Native input can be combined in one CLI turn; delivery into MCP, a reply-tool call and a response boundary are distinct. `attached` means MCP initialized, not that Claude registered or executed a message. Permission previews may already be normalized/redacted/omitted upstream; unsuitable previews are refused remotely. Codes bind one native request and expire after five minutes, but sending a verdict cannot prove the CLI adopted it before a local decision. Native mode follows existing CLI permission rules; it does not force every read or previously allowed action to prompt.

Native successful receipt/forwarding is silent. The broker returns the reply body without a fixed task-result/unverified prefix; bounded text filtering remains. The channel instructions ask for natural conversation and evidence-based work reports, while permission requests and actionable errors still reach WeChat. MCP/forward/reply counters live in the desktop's collapsed connection details. This changes presentation, not the evidence required to claim task success.

Native `/cancel` pauses new forwarding, removes unforwarded messages and sends denials for pending remote requests. It cannot withdraw input already in Claude or stop an active tool. App disconnect/quit closes this relay, not necessarily the independent CLI. Actual interruption is **Ctrl+C in the original terminal**. New sessions are handled there too; the API queue/turn/time/cost limits below do not apply to native execution.

## API agent in the released baseline

WeChat iLink HTTPS long poll → owner-only timestamped text → bounded serial Dispatcher → official Claude Agent SDK/native subprocess → correlated one-time permission/question → same owner's reply. Electron main orchestrates `src/bot` asynchronously; the SDK executes in a separate native process. This is independent of the observer below and does not install user hooks.

Connections never start automatically. One owner/project/connection has one explicit SDK session ID; subsequent prompts use `resume`, never global `continue`. One active task plus three queued tasks, 24 turns, ten minutes, bounded history and an SDK cost threshold limit work. Task state and send failure are separate. Disconnect and quit abort execution, invalidate permissions and wait for the old runner to settle before a new connection. No durable replay is attempted.

Every known tool is forced through a fail-closed `PreToolUse` ask rule, then a callback bound to a 128-bit, five-minute, single-use request. Unknown tools are denied. Tool/task cancellation, expiry and disconnect invalidate permissions. Oversized or secret-filtered parameters cannot be authorized from an altered display. This is authorization, not OS containment: approved Windows commands can affect the whole local account.

OS-encrypted API/WeChat credentials never enter renderer snapshots. In API mode, ambient user/project settings, OAuth, hooks, plugins and MCP are excluded. SDK sessions persist locally; the bounded bot UI transcript is memory-only. Tencent and Anthropic receive data needed for the flow. See [WeChat setup/limits](WECHAT.md), [source review](BOT_TECH_NOTES.md), and [third-party terms](../THIRD_PARTY_NOTICES.md). A basic native live flow passed with preview.1; API live acceptance and preview.2's reply pre-allowance remain pending. [Validation](VALIDATION.md) separates those from fixtures.

## Existing local observer

Claude Code command hook → allowlisted metadata → atomic local inbox file → Electron main-process reducer → isolated renderer.

The short-lived Node observer reads stdin, caps input at 2 MiB, writes one uniquely named JSON file, produces no output, and exits 0 even if observation fails. It times out after 1.5 seconds. It does not parse transcripts, approve commands, call a server, or keep a process alive. Claude's configured hook timeout is 2 seconds.

The main process polls once per second, sorts received events by observation time, rejects invalid payloads and duplicate IDs, and ignores events older than a station's latest timestamp. It persists state atomically before deleting consumed inbox files, so a crash replay is idempotent. A single-instance lock prevents competing consumers. Processing is bounded at 500 files per tick and 200 stations. Event history is capped at 30 entries per station. Full renderer snapshots are sent only when their contents change; relative ages update locally, while the poll still checks the five-minute uncertainty boundary.

Station keys are tuples of session ID and agent ID, not project folder names. Existing stations keep their positions as events arrive; new stations appear first. Tool failures are recoverable, API failures are separate, and closed parent sessions do not imply child success. The UI marks active observations older than five minutes as uncertain without changing the stored observation.

`PermissionRequest` does not include `tool_use_id`. The observer computes an HMAC of canonical tool input, session, agent and tool using a random local 32-byte `observer-key`. Only the opaque digest is stored, never the input. The reducer matches a permission to a unique pending `PreToolUse` digest and its tool ID. A completion for a different tool cannot clear that permission. Missing input or identical concurrent inputs cannot be resolved reliably: after activity the station becomes uncertain instead of guessing. This also applies to old inbox events without correlation metadata.

Pending approvals and questions are bounded to 100 entries. Overflow retains an unresolved marker across restarts; completing the retained entries cannot make discarded approvals look resolved. AskUserQuestion and ExitPlanMode keep their input-request meaning through generic permission notifications. Older parent-close events cannot rewind newer child observations; a newly uncertain child becomes visible for attention again.

## Limits of observation

- Hook events are observations, not a comprehensive process supervisor. A crash, interrupted CLI, lost event, or very long tool may produce an uncertain station.
- Ordering uses local hook-receipt timestamps. Parallel processes and OS scheduling can reorder observations. Completed tool IDs suppress late permission/pre-tool events within a turn; arbitrary distributed-clock reconciliation is not provided.
- `Stop` is emitted during hook processing; another Stop hook may continue the turn. “Response ended” means a response boundary was observed. Subsequent activity returns the character to work. No success status exists.
- `background_tasks` prevents showing done while known background work remains. `session_crons` displays idle for scheduled wakeups. Older versions may omit those fields.
- `SubagentStop` has the parent's background registry, so those arrays are intentionally ignored for child completion. Internal Claude agents can also produce subagent events.
- AskUserQuestion is identified from `PreToolUse`; approval and relevant notifications identify other waiting states. This app cannot guarantee detection of every UI prompt in every Claude version.
- Hooks do not expose the instant a person approves a tool. The last observed permission request remains visible until the next tool/result event, potentially for the duration of a long-running approved tool. The scene is an observation record, not a continuous execution monitor.
- `idle_prompt` is a reminder after a response, not evidence of a pending approval, and is ignored. Events within one poll are coalesced per station before notification; a wait that already recovered does not trigger an obsolete attention alert.
- Quiet notifications use a 15-second per-station cooldown, suppress focus and old backlog, and never contain reply text. A rapid second transition can intentionally be suppressed; the current scene remains authoritative.
- Demo state is separate from real state and never generates desktop notifications.

## Storage

Default directory: `~/.agent-arcade/`. `config.json` holds preferences; `state.json` holds stations/history; `inbox/` holds queued metadata; `bin/` holds installed observer copies; `theme.json` holds one custom theme; `observer-key` salts private tool correlation. Do not publish this key with support reports. App UI data is not hosted. `AGENT_ARCADE_HOME` and `AGENT_ARCADE_CLAUDE_SETTINGS` isolate integration tests; set the home variable in both app and hook environments when overriding it.
